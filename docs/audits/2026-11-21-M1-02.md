## Findings
1. **[high] All substeps in a frame use the last `dt` written.** `encodeSubstep` calls `queue.writeBuffer(uniformBuffer, …dt…)` per substep, but `encodeFrame` records every substep into **one** encoder and submits once. All queued `writeBuffer`s land before the submitted commands run, so every substep reads the final `dt`. At 512² today, every frame hits the 64-substep cap with an identical `dt`, so it's hidden. It shows up as soon as a frame finishes its sim time inside the cap (smaller grids, M1-06's larger steps, later variable frame times): the short final `dt` gets applied to *all* substeps. The sim then runs slower than `simTimeAdvanced` claims, and the throughput number is wrong.
   **Fix:** a uniform **ring with dynamic offsets**: `MAX_SUBSTEPS_PER_FRAME` slots, each 256-byte aligned, written in one `writeBuffer` per frame. Bind with `hasDynamicOffset: true` and pass `slot × 256` to `setBindGroup`. (Separate submits per substep also work, but cost more.)
2. **[medium] Compare-to-CPU doesn't exercise the paths that matter.** It runs a level canvas with one frozen `dt` in one encoder, so it couldn't catch finding 1, and it never tests upwind gravity or drain. **Fix:** extend the harness with (a) a **mixed-dt** sequence through the real `encodeFrame` path, and (b) a **tilted** case with a puddle near the edge, comparing drained volume too. The overlay shows all three results.
3. **[medium] `hMaxHint` only ever grows, and is never measured.** The timestep uses `hMaxHint`, which is raised on height writes but never lowered or read back from the GPU. Today that's safe but pessimistic: as the puddle spreads from 1.5 mm, the true stable `dt` grows as 1/h³, but the sim keeps the initial tiny step, so the reported throughput undersells the solver. In M1-04, pouring adds height *on the GPU* and the hint won't see it, which is **unsafe**. **Fix:** a GPU max-reduction of `h`, read back asynchronously at most every ~10 frames, with a 10% safety margin. Any CPU-side height write or pour deposit raises the hint immediately.
4. **[medium, → M1-04] The drain counter overflows at 4.3 ml, and truncates.** `flow_update.wgsl` accumulates drain as `atomic<u32>` micro-mm³: the maximum is 4.29e9 µmm³ ≈ **4,295 mm³ ≈ 4.3 ml** before it wraps (the test above drained 725 mm³ from a tiny puddle), and each `u32()` truncation drops up to 1 µmm³. At 512² that's up to ~2,000 border cells × 64 substeps per frame. M1-04's accounting rule (poured = canvas + drained) will fail. `syncDrainFromGpu` also isn't called anywhere yet. **Fix in M1-04:** per-border-cell `f32` accumulators (one slot per border face, owned by one thread, no atomics), summed in float64 on the CPU at sync, then cleared.
5. **[low → Discovered]** On the GPU, `hNew < −1e-6` is silently set to 0, where the CPU throws. Add a debug counter (an atomic incremented when it triggers) and show it in the overlay. If the limiter is correct it stays 0, and it's a cheap tripwire.
6. **[info]** Throughput is 64 substeps/frame, ≈ 0.006–0.012 sim-s per wall-s at 512², so 1 s of paint flow takes 80–160 s. That's exactly what ADR 0003 predicted, and M1-06 is the remedy.
7. **[info]** The square grid is still stretched across the window. That's already an M1-05 criterion.
